## Economic effects

SignBridge-TR is an assistive-communication prototype for short exchanges between Turkish Sign Language (TİD) users and Turkish speakers in service settings such as hospital desks, pharmacies, classrooms and cafés [E1]. Its economic effects are discussed here at two levels: the cost of building and running the prototype within the senior project, and the wider effects the product could have if it were developed further. No figure in this section is a measured expense or a measured benefit.

**Spending recorded so far.** The project records (Jira, the GitHub repository and the Confluence space) contain no project expenditure. The tools used up to Sprint 3 are listed in proposal Table 5 as free or available under student licences: Python, PyTorch, MediaPipe, Blender, Three.js, React/Next.js, FastAPI, Jira, Confluence and GitHub [E1]. The SB-40 avatar pilot used Blender, Three.js (MIT licence), Node.js and a headless Chromium browser, with no paid service [E3]. These records do not show whether a team member paid for anything privately. Such spending, if any, has not been reported to the team.

**Development cost items.** Table E-1 lists the cost items of the project and shows whether each one is recorded, estimated or not yet calculable. The quantities that drive each cost are named, so that the estimates can be filled in once those quantities are known.

*Table E-1 – Development and operating cost items*

**Potential student support.** The SE 4910 Week 5 slides (29 Oct 2026) list two student offers: Azure for Students, described as USD 100 of cloud credit plus some free-tier services, and the GitHub Student Developer Pack, which lists Azure for Students among its cloud offers [E6]. The team has not verified whether these offers can be combined, whether any member has activated them, or whether they would cover the hosting and API costs above. They are therefore shown only as potential support and are not included in any budget or cost estimate.

**Effects outside the project.** If the prototype were developed further, its main economic effects would come from making short exchanges possible without booking an interpreter or relying on written notes [E1]:

- *Time and resources.* For short, routine exchanges within the supported vocabulary, users could avoid waiting for an interpreter appointment. No time saving has been measured. Task completion is an evaluation target (O7), not a result [E5].
- *Employment.* The prototype is intended to support short, routine exchanges within a limited vocabulary of isolated signs [E1]. Situations that require professional interpretation, such as clinical decisions, are outside the project scope [E1]. The effect of the product on interpreter employment, or on other jobs, has not been assessed.
- *Revenue streams.* No business model is part of the project scope. Any later commercial use would be limited by licence terms. AUTSL may be used only for academic, non-commercial purposes [E1]. In the SB-40 pilot, the two TİD examples ÇOK and TEYZE are adaptations of SIGN-HUB reference poses and are shared under CC BY-NC-SA 4.0 [E3], [E7]. This licence statement does not apply to the two synthetic test clips (index and four-finger curls), which are original test movements [E3]. Commercial use would therefore need new training data or licences, and newly authored or relicensed versions of any clips derived from non-commercial references. This cost is not calculable yet.
- *Economic sustainability.* Running costs after the project would depend on paid API use, hosting and the effort needed to keep the clip library and the model up to date. These are assessed in the next section.

## Manufacturability, Productivity and Sustainability

SignBridge-TR is a software product with no hardware of its own. It runs as a progressive web application on phones, tablets and computers that users already have [E1]. In this project, "manufacturability" therefore means whether the model, the lexicon and the avatar content can be produced, updated and maintained with the planned methods and effort. Productivity and sustainability depend mainly on the work these assets require and on the external services the product uses. This section follows the major risks listed in proposal Table 1 [E1].

**Processing locations and dependencies.** Table M-1 shows where each part of the system runs according to SB-41 and the proposal data-flow table [E1], [E2]. Several choices are still open; they are marked as such.

*Table M-1 – Processing locations and external dependencies*

| Function | Where it runs | External dependency | Status |
|---|---|---|---|
| Camera capture and landmark extraction | On the device (MediaPipe in the browser). Raw camera video never leaves the device | MediaPipe library and the browser's camera and WebGL/WASM support | Required design; device support depends on the first benchmark [E2] |
| Sign classification | On the device, or optionally on the project back end using only landmark sequences | Own back end if the server path is selected | Deployment choice open [E2] |
| Turkish speech-to-text | Browser, local model or remote provider | Speech provider or browser vendor | Provider, retention and offline support unverified [E2] |
| Gloss → Turkish and Turkish → gloss | Project back end with a local or external LLM, plus the rule layer and lexicon | LLM provider if an external model is chosen | Provider open [E1], [E2] |
| Text-to-speech | Browser, local engine or remote provider | TTS provider if a remote engine is chosen | Provider open [E2] |
| Avatar playback | On the device (Three.js/WebGL), loading glTF/GLB clips from the application | Three.js and the browser's WebGL support | Playback shown in the SB-40 pilot on one desktop setup; mobile playback untested [E3] |

**Producing and updating the recognition model.** The model is trained offline on landmarks extracted from an existing dataset, AUTSL, or BosphorusSign22k if AUTSL cannot be used. It is exported to ONNX or TensorFlow.js for use in the browser [E1]. Reproducible extraction and preprocessing scripts and a data card are planned (deliverable 5), so that the model can be retrained when the vocabulary changes [E1]. Training and the browser must use the same MediaPipe version and point schema [E1]. A MediaPipe update could therefore require re-extracting the landmarks and retraining the model. Pinning versions and recording them with each model export (SB-41) reduces this risk. The main production risk is data: the dataset may not cover the target signs, and the model may not generalise to new signers, lighting conditions or backgrounds (proposal Table 1) [E1].

**Producing and updating the lexicon.** The lexicon is a JSON file that links each gloss to its Turkish equivalents, its domain and its clip file (deliverable 3) [E1]. Adding a sign means adding a lexicon entry and its clip and repeating the reference and review checks. The Turkish → gloss rules are planned to be reviewed by a TİD expert where available [E1]. The scenario coverage audit that fixes the MVP vocabulary is planned in proposal Methods 1 [E1] and is still marked as pending [E8].

**Producing and updating the avatar content.** The SB-40 pilot produced four short clips: two synthetic finger curls and two manual approximations of documented TİD signs, ÇOK and TEYZE [E3]. All were authored with Blender keyframes, exported as GLB and played with Three.js in Chromium. The pilot found and fixed three export problems: a generic clip name, an extra frame in the clip length and a previous action carried into the next export. This shows that the production pipeline needs scripted checks; the pilot's `verify.mjs` checker is an example [E3]. The pilot does **not** establish the following: the effort needed to produce 300 signs, the linguistic accuracy of the clips, whether TİD users understand them, facial and mouth movement, two-handed signs or mobile performance [E3], [E2]. The script run times recorded in the pilot measure the scripts only, not human authoring time [E3]. They are therefore not used here as a production rate. Clip production capacity remains a major risk (proposal Table 1). SB-25 Gate B proposes the next step: a 5–10-sign pilot that records rig preparation, authoring, correction, review and export time separately. The 300-sign target is kept until any change is decided with the advisor [E1], [E4].

**Asset rights.** Engine licences do not cover characters, motion files, reference videos or derived clips [E4]. Each rig, each reference source and each derived clip needs its own licence check before it is used or published [E2], [E4]. Of the current pilot clips, only ÇOK and TEYZE, which are adapted from SIGN-HUB references, are under CC BY-NC-SA 4.0 and limited to non-commercial use [E3], [E7]. The two synthetic test clips are original test movements and are not covered by that licence statement [E3].

**External services: outages, quotas, prices and versions.** The speech, LLM and TTS services are the main sustainability risk. A provider may stop a service, change quotas or prices, change data-retention terms or retire a model version. Proposal Table 1 rates the risk that AI services become paid or unavailable as medium likelihood and low impact [E1]. The planned responses differ in maturity:

- *Documented requirements (SB-41).* Record the provider, version, payload, destination, region, logging and retention for each selected path. Keep project-managed credentials on the server. Test timeouts, service outages and network interruptions, including retry and correction and keeping draft text where applicable [E2].
- *Proposed, not yet technically validated.* Place the services behind one service interface, with open-source alternatives (local Whisper, an open-source LLM, Piper TTS), and cache frequent sentences and responses [E1]. Typed text is a proposed fallback when speech-to-text fails, and fingerspelling covers words that are not in the clip library [E2], [E5]. None of these alternatives has been tested yet. Switching to a different model may change accuracy, latency and resource needs. The affected criteria (O2, O3, O5) would then need to be measured again [E5].
- *Version compatibility.* A new model or provider version can change outputs without any code change. Each evaluation run therefore records the build, model or service version, device, browser and date (SB-24 §4.6 and SB-41) [E2], [E5]. Browser support for camera, microphone, PWA and WebGL varies by platform and is not yet verified across browsers [E2].

**Productivity.** The product aims to make short exchanges possible without an interpreter appointment. It also aims to make repeated exchanges faster with quick phrases and cached responses [E1]. No productivity gain has been measured. Task completion, SUS and latency are evaluation targets (O5, O7), not results [E5]. On the development side, scripted asset generation and verification, a shared lexicon schema and reproducible preprocessing scripts are intended to make it easier to add vocabulary later. How much effort they save has not been measured.

**Sustainability.** On-device landmark extraction avoids uploading video. Server-side processing is limited to text, optional landmark sequences and the selected speech services [E1], [E2]. No energy, carbon or cost saving is claimed for this design, because none has been measured. After the project, the system can be kept running only if four things are maintained: the licences and storage for the clip library, a funded or open-source path for the speech and language services, the hosting environment, and a person responsible for updating the model and the lexicon. How the system will be maintained after June 2027 has not been decided.
